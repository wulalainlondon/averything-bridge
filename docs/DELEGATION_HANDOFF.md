# Coordinator handoff reminder on durable delegation returns

This optional feature appends coordinator-maintained context to an existing durable delegation result. Children continue to provide their own results. The original result projection, artifacts, native/source identity, permissions, sourcebinding and execution/delivery state machine remain in charge. This is an aid to continuity, not a guarantee that work will never be missed.

## Enable for one parent

Default is off. In a reviewed server startup configuration, add:

```
--delegation-handoff-config /existing/authorized/workspace/handoff-config.json
```

See `examples/delegation-handoff-config.json`. Replace the exact parent session ID, canonical absolute workspace and relative handoff path with explicitly authorized values. There is no default/wildcard parent or child-text path discovery. The workspace must equal the parent's current canonical workspace and remain inside the Bridge root when restricted. Paths never expand scope. The CLI file is operator-owned; this does not add an agent tool or grant to change server configuration. A human or coordinator may specify the path within existing authorization, then the normal reviewed deployment/configuration process loads it. No live reload or automatic restart.

The file follows `examples/coordinator-handoff.json`: schema version 1, positive integer revision, RFC3339 updated_at, and nonempty goal/progress/next_step strings. A coordinator maintains these fields using existing authorized editing tools. Increment revision for every byte/content change; do not write unverified work as complete. Atomic replace is recommended. An optional expected_revision/expected_sha256 in the parent policy pins an exact version; updating beyond the pin yields unavailable until an authorized configuration change. Without a pin, Bridge selects the version observable during first return preparation, subject to freshness and revision checks.

Only versioned JSON is supported in this minimum implementation. No LLM calls, Markdown summarizer, goals/ETA system, command execution, private-file scan or KB lookup is added.

## Bounds and trust

Configuration is <=64 KiB with <=100 explicitly keyed parents. Every handoff JSON parse (configuration, document, or stored snapshot) checks its byte bound before the duplicate-key prepass. The prepass rejects a ninth container before descending; at most eight containers may be nested (the configuration schema needs three). Trailing values are rejected before typed decoding. Each file is <=16 KiB; the three summary fields are each <=1024 UTF-8 bytes. The appended reminder is <=6 KiB, including its warning and quoted metadata. Escaping expansion that exceeds the bound becomes unavailable while retaining bounded file/identity metadata. Encoded configured full path is <=2048 bytes. Malformed/duplicate JSON keys, unknown fields, binary/control data and missing metadata are rejected.

Workspace traversal uses confined Go root handles and identity checks. Symlink directory/file components are rejected, even when a symlink could remain within scope. Nonregular files and unreadable files fail closed; Unix nonblocking/no-follow open prevents FIFO/device substitution from blocking. File bytes are read twice through the same descriptor, with identity/stat/path-entry checks to detect in-place updates or atomic replacement during the read. On other systems Go Root confinement remains active; Unix-specific open flags are not available. Darwin validation is provided; other runtime platforms require their own source QA.

New document updated_at text is <=35 bytes before time parsing (RFC3339 with at most nine fractional digits and a numeric offset), and accepted values are stored as canonical UTC RFC3339Nano. Oversize time text becomes unavailable; after a stable read and valid schema/revision, the snapshot still carries the exact file SHA and revision, configured path and capture time. Rejected raw time text is not projected; the exact-file SHA retains its byte association. updated_at older than max_age_seconds (default 86400, configurable up to 30 days) or over one minute in the future fails. File mtime is used for race detection, not as evidence of coordinator progress. SHA-256 is over the exact file bytes, not a reserialized document. Revision rollback or reusing a revision with different bytes is rejected against a durable per-parent/path watermark; different parents keep separate watermarks. A timestamp supplied by a malicious writer cannot prove freshness or trustworthy progress. Keep write access to the handoff scoped to its coordinator owner. This feature labels context as untrusted; it cannot technically guarantee an LLM will ignore a malicious instruction, and it grants no permission.

## Durable snapshot and failure behavior

Before the first enqueue, Bridge persists an additive immutable return context keyed by delegation ID and bound to the original parent/child/request/source-thread/configuration tuple and exact sealed result/artifact/error identity. The reminder carries delegation ID, result SHA, configured file path, file SHA, revision, updated_at and capture time. The result SHA covers the full original result, including text beyond the existing return projection's 16000-rune limit; `bridge_sessions.read_result` retains the full result.

Available, unavailable and disabled snapshots all remain fixed for that return receipt. Stored-snapshot decoding has an eight-container and 64 KiB compatibility bound, so earlier accepted long-time snapshots remain readable without rewriting their saved snapshot or content. Both the ordinary read and first-writer transaction replay use the same bounded decoder. New bounded reminders normalize legacy time text only with a parser input of <=16 KiB; they retain delegation/result/path/file/revision/capture association when summaries are removed. Invalid internal metadata beyond the existing encoded path/identity bounds uses a stable `sha256:<digest>` placeholder instead of dropping all associations. Such a placeholder describes rejected bytes, not a usable path, time, result SHA or authority. Valid configured metadata is preserved; bounds never shorten the true child result or change sourcebinding. Restart/replay/configuration edits/file repair never retake the snapshot or rewrite the queue payload. A crash after receipt acceptance but before marking delivery queued reuses the original receipt without re-enqueueing. Old already-queued receipts keep their original payload and have no retroactive handoff association. Sourcebinding guards still run before send/recovery. Handoff snapshots do not mark execution or QA complete, change grants or authorize external actions.

Read/validation failure appends `status=unavailable` with a bounded reason and preserves the true child result. There is no separate read-failure retry loop or new return request. Storage errors follow the existing durable scheduler error behavior; no enqueue bypasses snapshot durability. Once a read-failure snapshot is saved, file repair only affects a later delegation return. First snapshot insertion and watermark update are transactional; concurrent preparations converge on one saved context.

“Latest” means the file snapshot at first return preparation. A later write, including one after the last stat check, can occur before native receipt consumption. Bridge does not claim that a previously queued message dynamically contains all later updates. Review the quoted version/path against the coordinator's current handoff when continuing.

The new tables `delegation_return_contexts` and `delegation_handoff_revisions` are additive in the existing delegation database; snapshot creation never rewrites task ledger completion/delivery fields. Preserve both tables and receipts on rollback. The immutable context is an audit association, not additional authorization. Retention/compaction and UI rendering of these associations are outside this bounded feature.

## Review and verification

Run `go test ./internal/handoff`, focused `TestHandoff` core tests, and the existing delegation P1 correction/sourcebinding/recovery tests. Fixtures use temporary workspaces and SQLite stores, with synthetic executors; they make no native/paid LLM calls. Independent QA must review the exact source freeze before deployment. No production enablement is implied by adding examples.
